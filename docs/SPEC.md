# Keryx Image Generation PoC Specification

## Goal

Demonstrate that Keryx can treat an image-generation model as both the resident PoM working set and the inference engine on a private devnet, using one VRAM copy and pausing PoM only while image inference occupies the GPU.

## User Outcome

A user opens a local web application, enters a prompt and deterministic generation parameters, submits a funded image request, observes request and miner status, and receives an IPFS-hosted image generated by a miner holding the registered model.

## Goals

- Run an isolated Keryx devnet that cannot affect official networks.
- Keep one supported image model resident in RTX 3070 VRAM.
- Make PoM read the inference runtime's resident model tensors.
- Pause and synchronize PoM before image generation.
- Resume PoM over the same tensor pointers without reloading weights.
- Publish generated images to IPFS and commit their CIDs through the devnet.
- Ensure one image request pays at most one assigned miner.
- Recover safely when a miner claims a request but misses its deadline.
- Provide a minimal web demonstration after the backend works.
- Produce reproducible evidence suitable for an upstream proposal.

## Non-Goals

- Mainnet or official testnet deployment
- Embedding models or semantic image search
- Chat or generic multimodal inference
- Arbitrary model marketplace support
- LoRAs, ControlNet, upscaling, video, or image editing in the first slice
- Remote tensor parallelism or pooling VRAM across internet miners
- Browser wallet integration in the first web demo
- Production content moderation policy
- Cryptographic proof that an image semantically matches its prompt
- Native image inference code written from scratch

## Selected Model

Start with a stable-diffusion.cpp-compatible SD 1.5 GGUF at 512x512 and batch size one. It is deliberately conservative for an 8 GB RTX 3070 and leaves room for inference activations and PoM metadata. SDXL is a follow-up only after zero-copy residency is measured and stable.

## Runtime Architecture

`libkeryx-sd.so` owns the stable-diffusion.cpp context and loaded tensors. Rust dynamically loads a small C ABI, mirroring `llama_engine.rs`.

PoM registration sequence:

1. Load the GGUF through stable-diffusion.cpp.
2. Enumerate all model tensors in canonical name order.
3. Record each tensor's logical name, canonical byte length, storage type, host/device location, and CUDA pointer when resident.
4. Compare sampled resident bytes with the canonical GGUF `WeightIndex`.
5. Refuse PoM installation when byte identity cannot be established.
6. Build PoM gather metadata over the accepted resident pointers.

Inference sequence:

1. Detect a supported image request.
2. Acquire exclusive access to the serving GPU.
3. Prevent new PoM launches and synchronize the active PoM stream.
4. Generate one image using the already-loaded model.
5. Encode and pin the result to IPFS.
6. Broadcast an image response committing to the request and result CID.
7. Release temporary inference allocations.
8. Resume PoM with the existing model context and tensor pointers.

## Initial Request Contract

The first protocol draft needs only:

```text
model_id
prompt
negative_prompt
width
height
steps
sampler
guidance
seed
reward
priority_fee
deadline
```

The first implementation may temporarily constrain width, height, sampler, guidance, and steps to network-approved values. Fixed parameters reduce consensus surface and simplify reproducibility.

One image request produces one image and one reward. A four-image UI action creates four independent requests with derived seeds.

## Claim and Lease

The reward experiment should add explicit request ownership before inference:

1. A miner capable of the requested model broadcasts a signed claim.
2. Consensus accepts at most one active claim for a request.
3. The claim expires at a deterministic DAA score.
4. Only the active claimant may submit the payable response.
5. A valid response releases the request escrow once.
6. An expired claim reopens the request.
7. The request eventually expires and refunds the user when no miner completes it.

The exact UTXO construction is intentionally deferred until current escrow scripts and consensus transaction validation are traced end to end.

## Web Demonstration

The first web interface contains:

- Prompt and negative-prompt fields
- Seed
- Generate action
- Fixed model and image settings displayed read-only
- Suggested reward with an optional higher priority value
- Request, claim, generation, IPFS, and confirmation status
- Generated image
- Transaction and CID details

A local backend may hold the funded devnet key. Wallet integration is not required for the protocol demonstration.

## Safety Boundaries

- Devnet uses isolated state, ports, genesis/parameters, and explicit local peers.
- Image files are treated as untrusted input when retrieved from IPFS.
- The web service applies response-size and MIME validation.
- Private or sensitive prompts are unsupported because current requests and IPFS results are public.
- The PoC must describe output as model-resident and content-addressed, not cryptographically correct.

## Acceptance Criteria

- No process connects to official Keryx mainnet or testnet peers.
- The model is loaded once for a same-model mining/inference cycle.
- PoM scans pointers owned by the stable-diffusion.cpp model context.
- The byte-compatibility gate passes or fails closed with a useful diagnostic.
- Tensor pointers and model identity remain unchanged before and after image generation.
- PoM stops before generation and resumes afterward without CUDA races.
- A 512x512 image is generated successfully on the RTX 3070.
- The image is retrievable through its committed IPFS CID.
- With two miners, only the active claimant performs payable work.
- Claim timeout and requester refund paths are demonstrated.
- The web interface shows one complete request-to-image lifecycle.
- Exact build, launch, test, VRAM, latency, and transaction evidence is recorded.

## Maintainability Risks

- Carrying a large permanent stable-diffusion.cpp fork would be expensive. Keep the patch to a narrow tensor-introspection and Keryx ABI layer.
- Consensus rules for claims and escrow can create chain splits if ordering is ambiguous. All decisions must derive from canonical DAA/block state.
- Stable-diffusion.cpp may change internal tensor structures. Pin a tested upstream revision and isolate internal access behind one wrapper.
- CUDA contexts and streams from Rust and GGML must be synchronized explicitly.
- Supporting many models before one model works would multiply canonicalization and VRAM problems.
